# Decisions: named Claude sessions in one sandbox (2026-10-12)

Decided with the maintainer, one at a time. Context: an operator asked, via a peer sandbox's controller, for a relaunch to bring up two named, long-lived Claude Code sessions as background jobs, with `claude agents` in the pane, instead of one foreground claude. The request proposed `SANDY_CLAUDE_RESUME=<id>,<id>`. The maintainer asked for sessions by name, created when missing, and a way to adopt sessions set up before the feature existed. The codex half of the request (`--ask-for-approval never`) is #451 and is not part of this.

Claude Code 2.1.291 documents `claude --bg --resume <session-id>`: it "continues that session in the background under the same ID, or starts a copy and says so when the session is already running". `--resume` takes an id, or a search term only for the interactive picker, so sandy must turn a name into an id itself.

| # | Decision | Choice | Deciding reason |
|---|----------|--------|-----------------|
| 1 | How sessions are declared | One file per session, `.sandy/sessions/<slug>.md`. Front matter allows exactly `name` (required), `session` and `receives`. The body allows exactly two headings, `## On create` (the first prompt of a new session) and `## On resume` (sent once on each resume). Any other key or heading refuses the launch, naming the file and line. `.sandy/sessions/` is excluded from the `.sandy/Dockerfile` context hash. | One place per agent, which is how the operator edits them, and a format small enough to parse strictly without node or jq. `.sandy/` is read-only in the container, so an agent cannot rewrite its own instructions. Without the hash exclusion, editing a session file would re-prompt the Dockerfile approval and rebuild the project image. |
| 2 | Finding the session for a name | In order: the file's `session:` id; else sandy's own record of the binding; else exactly one transcript whose title equals `name`, adopted and recorded; else, with no match, a new session, recorded. Several title matches, or a `session:` or recorded id that does not exist in the sandbox, refuse the launch. | Identity is the file, which the operator controls, not a title an agent can `/rename`. A silent duplicate would orphan an agent's thread, so an ambiguous match never guesses. `session:` lets sessions set up before this feature be adopted exactly, and it is visible in git. |
| 3 | Shared settings and single receivers | Every session gets sandy's session-wide flags (model, effort, `bypassPermissions`, teammate mode) and the operator's `agent-args.claude`; `claude agents` gets the subset it accepts. `--continue`/`--resume` are replaced by decision 2. `receives:` takes values from a closed set, `cross_session` and `channels`, and at most one session may claim each; two claimants refuse the launch. `channels` routes the `--channels` flags, and `SANDY_CHANNELS` with no claimant refuses. `cross_session` routes the `accept` inbound posture (every other session pinned `refuse`) and the agent args of features that declare `receives: ["cross_session"]`. Per-session operator args live in `$SANDBOX_DIR/agent-args.claude.<slug>`. | Some things in a sandbox have exactly one receiver (a polled bot, an inbound messaging path). The rule is enforced, never assumed, can split channels and inbound between sessions, and reuses the manifest's published `receives` vocabulary rather than naming any consumer. Per-session args live where a repository cannot reach them, like `agent-args.<agent>`. |
| 4 | When session files apply | Interactive launches and `--start` only. `-p`, `--remote` and `--provision` ignore them with one notice line. `--new` never touches named sessions. Env-only `SANDY_CLAUDE_SESSIONS=0` gives a plain claude pane for one launch. | Each launch mode keeps its meaning, and nothing that discards an agent's thread is reachable by accident. Env-only, so a committed config cannot switch the operator's agents off. |
| 5 | Readiness | `--start` waits (bounded) until every declared session is running under its expected id. Otherwise it exits with a new code `9`, naming the session and the reason (not running, or running as a copy under another id), and leaves the container running. Per-session status is recorded in the session marker and in `--print-state` (`claude_sessions`, additive; `schema_version` stays 4). A foreground launch prints the same as a warning. | Exit `0` keeps meaning "usable", which is the class of bug sandy has fixed repeatedly (#151, the API-key modal, the theme picker). One agent failing must not take a healthy one down. |

Options considered and not taken:
- **1:** a config key listing names, with priming files found by a naming convention; a single `.sandy/sessions.json` manifest.
- **2:** title match each launch, newest wins; title match each launch, refuse on duplicates; plain recorded binding with no `session:` key; a `sandy --bind-session` command.
- **3:** one `primary: true` session that receives everything; per-session args files only, wired by hand; ignoring `SANDY_CHANNELS` with a warning; passing only agent args to background sessions.
- **4:** `--new` recreates every session; `--provision` creates the sessions.
- **5:** ready when the pane is up, with status reported only; tearing the container down on any failure.
- **Tier (raised before the shape changed):** an approval gate on the resume prompt text. Dropped once the text moved into `.sandy/sessions/`: a workspace already instructs every session through `CLAUDE.md`, and `.sandy/` is protected in the container.

To measure on the host before building (any result that breaks a decision is raised first):
1. The record Claude Code writes for a session's name in its `.jsonl` transcript.
2. Whether `claude --bg --resume <id>` after a container relaunch resumes under the same id or starts a copy, and whether the #407 registry prune is enough to prevent the copy.
3. Whether `claude agents --json` reports full session ids.
4. Whether a per-session `--settings` pinning `refuse` holds while another session in the same container gets `accept`, given the workspace `settings.local.json` copy is tighten-only.

Interface consumers learn about only once built: the requesting controller is told the final shape (session files, not `SANDY_CLAUDE_RESUME`) after the PR merges. Exit code `9` and `claude_sessions` need a sandy-ui release note.
