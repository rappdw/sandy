# Configuration

Every config key, the flags, and how per-project configuration is trusted. Part of the [sandy guides](README.md); back to the [project README](../../README.md).

## Per-project config (`.sandy/config`)

Sandy loads config from two levels, with project overriding user:

1. **User-level**: `~/.sandy/config` and `~/.sandy/.secrets` — apply to all projects on this machine
2. **Per-project**: `.sandy/config` and `.sandy/.secrets` — override user-level for this project

```bash
# ~/.sandy/config — user-level defaults for all projects
CLAUDE_CODE_OAUTH_TOKEN=sk-ant-...       # long-lived token (better in ~/.sandy/.secrets)

# .sandy/config — per-project overrides
SANDY_SSH=agent                          # use SSH agent instead of gh token
SANDY_MODEL=claude-sonnet-4-5-20250929   # override default model
```

Only allowlisted `KEY=VALUE` lines are parsed (not sourced as a shell script). Use `.secrets` files for credentials — they should not be committed. See the environment variables table below for supported keys.

| `SANDY_AGENT` | `claude` | AI agent(s) to run. | `SANDY_CPUS` | auto-detected | CPU limit for the container |

| `SANDY_SYMLINK_SCAN_SKIP` | (unset) | Comma-separated workspace-relative directories the launch's symlink scan leaves out, as it leaves out `node_modules/`, `.venv*/` and `.git/`. Entries are literal paths, spelled exactly as on disk; one that matches no directory is warned about. A link under a skipped directory gets no mount of its own and is never copied through, so one pointing outside the workspace dangles in the container. | `SANDY_EGRESS_STRICT` | `0` | **Deprecated** — use `SANDY_EGRESS=strict`. Still accepted with a warning; `1` selects strict mode |

| Flag | Description |
|---|---|
| `--help` | Show the usage summary and exit |
| `--version` | Print the version and exit. `-v` as the **only** argument does the same; with any other argument (even `--version` or `--help` after it) `-v` means verbose and sandy launches |
| `-v` / `-vv` / `-vvv` | Verbosity for this launch: `-v` shows the startup sections and pauses on exit, `-vv` adds a bash trace of the container setup, `-vvv` also traces the entrypoint and shows the docker flags. Same as `SANDY_VERBOSE=1\|2\|3`. `-v` on its own prints the version instead; with any other argument it means verbose, in any position (e.g. `sandy -v --new` or `sandy --new -v`) |
| `--workspace <path>` | Target workspace directory (default: the current directory). Honored by a plain launch (including `-p`, `--rebuild`, `--build-only`), `--start`, `--attach`, `--stop`, `--exec`, `--login`, `--update-sessions`, `--reset-sandbox`, `--remove-sandbox`, `--unlock`, `--ack-report`, `--provision`, `--approvals` and `--accounts` |
| `--new` | Start a fresh session (default: resume last) |
| `--resume` | Open session picker (claude's, or `codex resume` for codex) |

| `--rebuild` | Force rebuild of the Docker image |
| `--build-only` | Build images and exit (for CI) |
| `--no-update-check` | Skip update checks for this launch (one-shot `SANDY_OFFLINE=1`; wins over config). Works with a bare launch, `-p`, `--build-only` and `--start` |
| `--upgrade` | Update sandy to the latest version from GitHub |
| `--agent <list>` | Agent(s) to launch — overrides `SANDY_AGENT` and `.sandy/config` (e.g. `--agent claude,gemini`) |
| `-p "prompt"` | One-shot prompt (no interactive session) |
| `--start` | Start a detached [daemon session](daemon.md#daemon-mode) and return once attachable |
| `--attach` | Attach an interactive client to a running daemon session |
| `--stop` | Stop a running daemon session (full teardown) |
| `--ack-report` | Acknowledge the session-end report a [daemon session](daemon.md#the-session-end-report-of-a-daemon-session) left in its sandbox (protected paths that appeared, changed or were replaced in the workspace): prints it once more and removes it, so `--start`, `--attach`, `--stop` and terminal launches stop showing it. Filesystem-only. Exit `0` when no report is pending afterwards (including none to begin with), `1` otherwise. Sub-options: `--workspace PATH` |
| `--login codex` | Log codex in so its credential persists in this workspace's sandbox (`codex login --device-auth`), inside the running session if there is one, else in a one-shot launch. Sub-options: `--workspace PATH`, `--dry-run`. See [Running Codex CLI](agents.md#running-codex-cli-sandy_agentcodex) |
| `--exec [-- CMD]` | Shell (or run `CMD`) inside this workspace's running container, **as the host uid**. Do not hand-roll it: `docker exec -u sandy` resolves the name against the *image*, where the user is uid 1001, so it runs as the wrong owner and prints `I have no name!`. Sub-options: `--workspace PATH`, `--dry-run`. See [Getting a shell inside a running sandbox](daemon.md#getting-a-shell-inside-a-running-sandbox-sandy---exec) |
| `--stop-all` | **Fleet emergency stop** — stop every daemon session on the host via the hardened per-session teardown. Sub-options: `--dry-run`, `--yes` |
| `--prune-orphans` | Reap orphaned `sandy_*` Docker networks and exit |
| `--update-sessions` | Fleet image refresh + rolling restart across every daemon session on the host (scope to one with `--workspace PATH`). See [Fleet updates](daemon.md#fleet-updates---update-sessions). Sub-options: `--dry-run`, `--yes`, `--idle-for <minutes>`, `--rebuild`, `--workspace` |
| `--reset-sandbox` | Rebuild **one** project's sandbox from a known-good skeleton — destroy its persistent package/agent state (preserving `WORKSPACE.json` lineage), refusing while a live session holds it. Filesystem-only, no Docker. "When in doubt, rebuild" in one command. Sub-options: `--workspace PATH` (default cwd), `--all` (every sandbox sandy knows about), `--keep-history` / `--purge-history` (keep or wipe Claude's session transcripts and auto-memory under `claude/projects/`, and nothing else; asked interactively, **required** without a terminal, and not answered by `--yes`), `--keep-approvals`, `--dry-run`, `--yes` |
| `--rsync HOST` | **Copy** this workspace's sandbox to another host, even when the workspace lives at a different path there: renames it for the destination and rewrites the path-keyed state a hand `rsync` gets wrong (session history and memory, `.claude.json`, `WORKSPACE.json`). The destination workspace defaults to the same path under `$HOME` (`--dest-workspace PATH` to override). If there is no workspace there, the workspace itself is copied first, whole: `.git`, untracked and ignored files. A workspace that already exists there is never touched. Credential files are copied and named in the plan; on a different CPU architecture the package caches (and the workspace's `.venv/` and `node_modules/`) are skipped and rebuild on first use. Sub-options: `--workspace PATH`, `--dest-workspace PATH`, `--dest-sandy-home PATH` (the sandy home on the destination, if not `~/.sandy`), `--no-workspace` (sandbox only; the workspace must already be there), `--exclude PATTERN` (repeatable; keep paths out of the workspace copy), `--dry-run`, `--yes` |
| `--rsync-from HOST` | The reverse: **pull** the other host's sandbox for this workspace to this machine, using only outbound `ssh`/`rsync` from here, so it works when the other host cannot reach you (NAT, VPN). It is named for this machine's workspace path, with the same rewrites and the same plan. The source workspace defaults to the same path under `$HOME` on the remote (`--src-workspace PATH` to override). Name a `--workspace PATH` that does not exist here and the workspace is pulled too. Nothing is installed unless every step succeeds, and it never overwrites a sandbox or workspace already here. Sub-options: `--workspace PATH`, `--src-workspace PATH`, `--src-sandy-home PATH` (the sandy home on the remote, if not `~/.sandy`), `--no-workspace`, `--exclude PATTERN`, `--dry-run`, `--yes` |
| `--remove-sandbox` | Permanently delete a sandbox directory (preserves **nothing**, unlike `--reset-sandbox`). Three selectors: default/`--workspace PATH` (workspace must still exist), `--sandbox NAME` (workspace already gone), `--orphans` (every sandbox whose recorded workspace is gone). Filesystem-only. Sub-options: `--dry-run`, `--yes` |
| `--unlock` | macOS: clear the file locks (`chflags uchg`) a launch set on `.claude/settings.json`, `.claude/settings.local.json`, `.gemini/settings.json`, `.gemini/.env`, `.mcp.json`, `.envrc`, `.pre-commit-config.yaml`, `.mise.toml`, `.gitmodules`, the git config files and the `.git` file when its session ended without clearing them (normally the session's own cleanup, the next launch, or `--stop` clears them). Only what sandy set, on the same file; a flag you set yourself is never touched. Refuses while a session of the workspace runs, or while its container may still exist (one that outlived its session: remove it with `docker rm -f sandy-<sandbox>` first). If Docker cannot be reached it says so and prints the `chflags -h nouchg <file>` command for each file it locked, so you can clear them yourself once you know no container of the workspace is running. It also refuses while another running session shares a git dir of the workspace (a superproject and one of its submodule checkouts), naming it: those locks are released when the last of the sessions ends. Exit `0` when no lock of sandy's is left, `1` otherwise. Sub-options: `--workspace PATH`, `--dry-run` |
| `--provision` | Non-interactively create one workspace's sandbox by running the **real launch path** once (start a detached session, confirm it's up, stop it) — never a flag that fabricates state. Safe no-op against a live session. **`--all`** does every sandbox sandy already knows about that is missing the per-sandbox state a launch creates (`pip/` since 2.6.0; `relay-state/` was the target from 2.2.0 through 2.5.x, but a launch no longer creates it) — the state `--reset-sandbox` leaves behind. Needs Docker. Sub-options: `--workspace PATH`, `--all`, `--dry-run`, `--yes` |
| `--doctor` | Host + runtime readiness check (bash 5 or newer, a warning only; git/curl/docker/PATH/credentials, plus image staleness and orphaned resources). Exit `0` iff every required host check passes; runtime findings are warnings. Sub-options: `--fix` (clear a dead lock, reap orphaned networks), `--yes` |
| `--gc` | One-shot global reclaim of leaked sandy Docker resources: dead-owner containers, orphaned `sandy_*` networks, orphaned per-project/skill images, dangling images. Sub-options: `--dry-run`, `--yes` |
| `--print-state` / `--print-schema` / `--print-version` / `--validate-config` | Machine-readable JSON introspection (runtime state / static schema / version). `--validate-config PATH` reports a config file's unknown key names, its privileged keys and their approval status; it does not check values, so a bad value is only caught at launch. Fast-path, no Docker needed for schema/version. See [`SPEC_INTROSPECTION.md`](../../SPEC_INTROSPECTION.md) |
| `--sizes` | With `--print-state` (full mode): also measure each sandbox's disk use (`du`) and report it as `size_bytes`, e.g. `sandy --print-state --sizes`. Without it `size_bytes` is `null`, because the walk is slow on a host with many large sandboxes (**changed in 2.9.0**: full mode used to always measure). `sizes_computed` in the output says whether the walk ran. `--print-state light --sizes`, any other `--option` after `--print-state` (such as `--sizes=1`), and `--sizes` as a launcher argument (`sandy --sizes`) are errors (exit `1`). The other introspection flags (`--print-schema`, `--print-version`, `--validate-config`) ignore it, as they ignore any extra argument. |
| `--approvals` | Before launching without a terminal (CI, cron, a UI with no pty), see what each approval gate would do for this workspace: privileged keys in its `.sandy/config`/`.sandy/.secrets` (dropped if unapproved), symlinks escaping it, and (2.12.0) a git directory outside it that its `.git` file names (both: launch refused), its `.sandy/Dockerfile` (base image used instead). One JSON document; key **names** only, never values. **Read-only** — it grants nothing; approve by launching once from a terminal. Exit `0` all approved or not applicable, `2` something pending/changed/refused, `1` no report. No Docker needed. Sub-options: `--workspace PATH` |
| `--accounts` | See which account each agent in each sandbox is signed in to (Claude Code; Codex's email and ChatGPT plan; Gemini's Google account): one row per agent the sandbox's last launch ran, grouped by sandbox, stopped sandboxes first and running ones last (nearest your prompt), in four columns: SANDBOX, AGENT, CRED (the kind of credential its last launch used: `full`, `oauth-token`, `api-key`, `chatgpt`, …) and ACCOUNT, which identifies it. For an account login ACCOUNT is the email that agent last recorded in the sandbox, not a live query: your login is read from the host at every launch, so a re-login shows up after the next session. A long-lived token from `claude setup-token`, or an API key, names no account and Anthropic will not report one for it, so ACCOUNT shows your label for it from `~/.sandy/credential-labels`, else its fingerprint (see `--fingerprint-token`). A fifth column, GITHUB, is the gh account sandy made active in that sandbox at its last launch (`--json`: `github.account` and `github.reason`). Organization, plan (e.g. `Max 20x`, `Team (standard)`) and record dates are in `--json` only. With credential mode `none` the account shown is not what billed. Prints personal data. No Docker needed. Sub-options: `--json` (one JSON document), `--workspace PATH` |
| `--fingerprint-token` | Print the fingerprint (8 hex digits of its sha256) of a token or API key you pipe in on stdin, e.g. `pbpaste \| sandy --fingerprint-token`; with a terminal it prompts with input hidden. A long-lived `CLAUDE_CODE_OAUTH_TOKEN` or an API key carries no account, so sandy records each launch's fingerprint and `--accounts` shows it under ACCOUNT. Name your tokens by adding `<fingerprint> <label>` lines to `~/.sandy/credential-labels` (e.g. `3fa1c09e corp` or `b8663216 personal (rappdw)`: the label is the rest of the line, spaces included), and ACCOUNT shows the label. A line that is not a label is named in a warning. Never pass the secret as an argument. No Docker needed. |

**`--start` exit codes:** `0` = ready, `6` = refused before launch (something needs a person at a terminal: an approval to answer, a missing or expired credential the agent would prompt for, a sandbox that needs migrating; the error names which), or a feature entry started and then exited inside its 5s startup window (**changed in 2.9.0: this was `7`**), `7` = container crash-looping (including a feature entry that cannot start at all), `8` = timed out waiting for the session, `9` = a named Claude session (`.sandy/sessions/`) did not come up (the container is left running; see [Named Claude sessions](agents.md#named-claude-sessions-sandysessions)).

**Approvals under `--start`.** Run from a terminal, `--start` asks every launch approval — privileged keys in a workspace config, symlinks that escape the workspace, a git directory outside the workspace that its `.git` file names (2.12.0), and a `.sandy/Dockerfile` build — on *that* terminal before it detaches, and only then starts the background session. The background session then scans the workspace again and checks what it finds against what was approved there: a symlink that escapes the workspace and was added or changed in between makes it refuse to start (`--start` exits `6`), naming the link, and the next terminal launch asks about it (or refuses it, once an approval exists). So `--start` scans twice; `SANDY_SYMLINK_SCAN_SKIP` shortens both scans. Declining a symlink stops `--start` with `6`; declining the Dockerfile does not — the session starts on the base agent image, as it would in the foreground. A client with no terminal at all can't be asked, so each gate fails closed unless approved earlier — `sandy --approvals` shows which ones would, before you launch; `SANDY_AUTO_APPROVE_PRIVILEGED=1` (env-only, for CI) bypasses the config-key and Dockerfile gates but **not** the symlink or git-directory gates, deliberately.

All other arguments are forwarded to the selected agent (claude, gemini, codex, opencode, grok, or mirror).

## Per-project secrets

`.sandy/.secrets` uses the same `KEY=VALUE` format as `.sandy/config` but is intended for credentials. Add it to `.gitignore`:

```
.sandy/.secrets
```

## Screenshot skill (`/ss`)

> **Deprecated since 2.0.0.** `SANDY_SCREENSHOT_DIR` still works, but it is listed in the README's [Deprecated](../../README.md#deprecated) table: it is meant to become a feature manifest, and the key stays until that design is settled.

Set `SANDY_SCREENSHOT_DIR=<host-path>` in `~/.sandy/config` (privileged tier — set freely here, or per-workspace `.sandy/config` with one-time approval) to give the agent **eyes**: sandy mounts the folder read-only into the container and generates a per-agent `/ss` skill that finds the newest screenshots and feeds them to the model.

```sh
# in ~/.sandy/config
SANDY_SCREENSHOT_DIR=/Users/you/Desktop/organized-screenshots
```

Usage inside a session:

```
/ss              # newest screenshot, no instruction → agent describes it
/ss huh          # newest screenshot + "huh" → agent explains
/ss 3 explain    # 3 newest screenshots, agent explains the set
/ss fix          # newest is an error message → agent diagnoses + fixes
/ss do this      # newest is a technique you saw → agent applies it
/ss make infographic  # newest N → agent synthesizes one
```

| Agent | How to invoke |
|---|---|
| Claude | `/ss [N] [action]` slash command |
| Gemini | `/ss [N] [action]` slash command |
| Codex  | "look at my recent screenshot" — codex matches by description |
| OpenCode | manual: `opencode "explain $(sandy-ss-paths 1)"` (no slash-command surface in v0) |

No default — leaving `SANDY_SCREENSHOT_DIR` unset disables the feature entirely. macOS users typically point at `~/Desktop` (the macOS default for `Cmd+Shift+4` captures) or a custom folder configured via `defaults write com.apple.screencapture location <path>`. The mount is read-only by design; the agent should never modify your screenshot folder.

Choose a specific directory: Sandy rejects `/` and your whole home directory, including symlink aliases of either path.
