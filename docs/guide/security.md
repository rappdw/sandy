# Security notes

What sandy protects in your workspace, and where the full threat model lives. Part of the [sandy guides](README.md); back to the [project README](../../README.md).

- The container runs as a non-root user (`sandy`, mapped to host UID)
- The root filesystem is read-only (`/tmp` and `/home/sandy` are tmpfs)
- `no-new-privileges` prevents privilege escalation
- Credentials are seeded into per-project sandboxes, not shared across projects
- claude.ai account connectors are suppressed by default (`SANDY_CLAUDE_CONNECTORS=1` to opt in); `SANDY_SUSPICIOUS=1` additionally strips the OAuth refresh token so a distrusted workspace only ever sees a short-lived access token
- Claude Code's own `/sandbox` (`sandbox.enabled`) is forced **off** in the sandbox's `settings.json` every launch, even if your host settings turn it on — sandy's container is the boundary and its egress proxy the one policy chokepoint, so an inner sandbox would only add a second, uncoordinated proxy. Your other `sandbox.*` settings are left as they are, and a repository's own `.claude/settings.json` can still turn it on (Claude Code gives project settings precedence)
- The working directory is bind-mounted read/write — Claude can modify your files there (that's the point)
## Protected files and directories

The workspace is bind-mounted read/write so Claude can modify your project files. However, certain files and directories are overlaid with read-only or sandbox mounts to block the most dangerous attack vectors for an AI coding agent: shell config injection, git hook injection, and tool config tampering.

**Read-only mounts** — host content is visible but cannot be modified:

| Path | Why |
|---|---|
| `.bashrc`, `.bash_profile`, `.zshrc`, `.zprofile`, `.profile` | Blocks shell config injection (e.g. aliases, PATH hijacking) |
| `.gitconfig` | Blocks git config tampering (e.g. credential helpers, aliases) |
| `.ripgreprc` | Blocks search config injection |
| `.mcp.json` | Blocks MCP server config tampering |
| `.envrc` | Blocks `direnv` auto-sourcing (executes on `cd`) |
| `.tool-versions`, `.mise.toml`, `.nvmrc`, `.node-version`, `.python-version`, `.ruby-version` | Blocks asdf/mise/nvm/pyenv/rbenv toolchain hijacking |
| `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pypirc`, `.netrc` | Blocks registry hijacking and credential exfiltration |
| `.pre-commit-config.yaml` | Blocks pre-commit hook injection |
| `.git/config`, `.gitmodules`, `.git/packed-refs`, `.git/commondir`, `.git/config.worktree` | Blocks git remote/hook path manipulation and ref spoofing (`.git/HEAD` is left writable so `git switch` works in-container — #80) |
| `.git/hooks/` | Blocks git hook injection (pre-commit, post-checkout, etc.) |
| `.git/info/` | Blocks `.git/info/attributes` filter-driver injection |
| `.git/modules/<sub>/{config,hooks,info,commondir,config.worktree}` | Same, for every submodule gitdir (found at any depth) |
| `.git/worktrees/<name>/` | Each linked worktree's whole admin directory is read-only (2.12.0): git in the session takes every linked worktree for gone (its `gitdir` file names a host path), so a `git worktree prune` or `git gc` there would delete them all. `worktrees/` itself stays writable, so `git worktree add` works; one removed while the session ran (in practice on the host, since the session cannot) is reported at session end, and the container's git never prunes worktrees or expires reflogs in `gc` (`gc.worktreePruneExpire`, `gc.reflogExpire` and `gc.reflogExpireUnreachable` are `never`; an explicit `git reflog expire --all` still fails in such a session, as it would write the other worktrees' read-only logs). Its `commondir` and `config.worktree` are protected as before: git run in that worktree reads them (2.9.0). One created during the session is reported at session end, as is a new submodule gitdir |
| `.vscode/`, `.idea/` | Blocks IDE task/launch config injection |
| `.github/workflows/` | Blocks CI pipeline escape (opt-out via `SANDY_ALLOW_WORKFLOW_EDIT=1`) |
| `.circleci/`, `.devcontainer/` | Blocks CircleCI and devcontainer escape |
| `.mirror/` | Blocks Mirror extension injection (Python that Mirror runs), 2.9.0 |
| `.claude/settings.json`, `.claude/settings.local.json`, `.claude/hooks/` | Blocks agent→host Claude Code hook injection (a host `claude` run in the same dir would otherwise execute an agent-written hook) |
| `.gemini/.env` | Blocks agent→host Gemini CLI injection: a host `gemini` run in the workspace loads every variable in it into its environment (2.10.0). Read-only in the session when it exists at launch; one created in-session is reported. A plain `.env` is watched instead (below) |
| `.gemini/settings.json` | Blocks agent→host Gemini CLI injection: its `mcpServers` are commands a host `gemini` run in the same dir would start (2.9.1). When it exists at launch it is read-only in the session, so Gemini CLI cannot save project-scope settings there (e.g. `gemini mcp add` at project scope fails) and edits to it do not persist |
| `.sandy/` | Blocks tampering with sandy's own build inputs **when `.sandy/` exists at launch** (existence-gated, like every row here — a session that starts without one can create it, and is warned about at session end). A per-project `.sandy/Dockerfile` build is additionally approval-gated by a hash of the whole build context, which is what stops a planted one from building unreviewed |

A redirected `core.hooksPath` (e.g. `.githooks/`) is resolved at launch and its target directory is mounted read-only too, so the protection follows git's actual hook path rather than only the default `.git/hooks/`. When `.git` is a file (a linked worktree or a submodule checkout), that file is mounted read-only as well, since it tells your git which directory to use.

**Links at the git paths sandy mounts (2.11.1).** A symbolic link at any path sandy mounts by name is approved at the dangerous-symlink prompt, wherever it points (headless and non-terminal launches refuse it until it is approved once). That includes the git paths sandy derives from the workspace: the directory a `.git` file names and its `config`, `hooks/`, `info/`, `commondir` and `config.worktree`, the same files of each submodule git directory and worktree admin directory, and the `core.hooksPath` directory. Before 2.11.1 a link there to a file outside your home directory was mounted read-only with no prompt.

**A git directory outside the workspace (2.12.0).** When your workspace's `.git` is a *file* (a submodule checkout, or a repository made with `git init --separate-git-dir`), it names the git directory git uses, and sandy mounts that directory read-write, because git must write its objects and refs. If the directory lies outside the workspace, sandy mounts it without asking only when it is this workspace's submodule git directory: the nearest repository that contains the workspace declares it as a submodule at this path in its `.gitmodules`, and the directory is the one git keeps for it, `.git/modules/<name>` (nested submodules included). Anything else, such as a `--separate-git-dir`, or a `.git` file that names another repository of yours (`gitdir: ../other/.git`), asks once:

```
[sandy] This workspace's .git file names a git directory outside the workspace:
[sandy]   gitdir: ../other/.git
[sandy]   which is /Users/you/dev/other/.git
...
[sandy] Mount it read-write for this workspace? [y/N]
```

Saying yes gives the agent read-write access to that repository's history (its objects, refs and branches; its config, hooks and info stay read-only), so say yes only for a directory you set up for this workspace. Sandy remembers the answer for this workspace and that directory, and asks again if the `.git` file later names a different one. A launch with no terminal (headless, `--start` from a script) refuses until you have approved it once from a terminal, and `SANDY_AUTO_APPROVE_PRIVILEGED` does not approve it. Before 2.12.0 any such directory was mounted read-write with no prompt. A git directory that is, or contains, your home directory or sandy's own state (`~/.sandy`) is refused outright, with no approval offered, and so is a launch where any file or directory sandy mounts read-only from that git directory (its `config`, `hooks/`, `info/`, and those of the submodules and worktrees under it) is a symbolic link: Docker would follow it. A `.git` file naming something that is not a git directory is still refused, as is a linked worktree made by `git worktree add` (support for those is planned).

**The directories above a protected path are pinned (2.9.0).** A read-only mount cannot be renamed or deleted inside the container, but a directory *above* it could be, which would carry the mount away with it. So each directory between the workspace root and something sandy mounts (typically `.git`, `.github`, `.claude`, `.gemini`, and `.git/modules/...` for submodules) is mounted onto itself, read-write. You and the agent can still change anything inside them, as before; only the directory itself cannot be moved aside or replaced. Sandy pins only directories that exist and are not symbolic links, so nothing new appears in your workspace. Two side effects: `mv` of a file between such a directory and the rest of the workspace becomes a copy and delete, and a protected path reached through a symlink (`.claude -> elsewhere-in-repo`) gets no pin, so since 2.9.0 such a link needs the same one-time approval as a symlink that points outside the workspace (a headless or non-terminal launch refuses until it is approved).

**A `commondir` for every git directory (2.9.0).** Git reads a file named `commondir` from any git directory, and one that doesn't exist can't be mounted read-only. So for the session sandy creates one containing `.` (the git directory itself, which is what git assumes anyway) wherever it is missing, protects it like the other git files, and removes it at the end if the session left it unchanged. When two sessions share a git directory (a superproject and a session of one of its submodule checkouts), its seed and its macOS locks stay until the last of them ends (2.12.0). While the session runs, `git rev-parse --git-common-dir` prints an absolute path instead of `.git`.

**Protected file contents are checked (2.9.0).** On a case-insensitive file system (the macOS default) a differently-cased name such as `.ENVRC` can reach the same file as `.envrc`, past its read-only mount. So sandy records the contents of every protected file at launch, keeps a private copy in the sandbox, and at session end lists any that changed, with a `diff` and `cp` you can run to compare and restore. It never restores anything itself. **On macOS** sandy also locks `.claude/settings.json`, `.claude/settings.local.json`, `.gemini/settings.json`, `.gemini/.env`, `.mcp.json`, `.envrc`, `.pre-commit-config.yaml`, `.mise.toml`, `.gitmodules`, `.git/config`, `.git/commondir`, `.git/config.worktree`, a `.git` file, each submodule's `config` under `.git/modules`, and (in a linked worktree or submodule checkout) the `config`, `commondir` and `config.worktree` of the git directory the `.git` file names (`chflags uchg`) for the session, so such a write fails; the launch prints which files it locked. While a session runs, host-side writes to those files fail too (for example `git config`, or Claude Code on the host saving `settings.local.json`). Sandy unlocks exactly what it locked when the session ends, at the workspace's next launch, or with `sandy --unlock`; a lock you set yourself is never touched.

**`.env` files are watched, not locked (2.10.0).** A Gemini CLI run on your host loads the nearest `.gemini/.env` or `.env` (looking from its directory upward) into its environment, so one written during a session changes your next host `gemini` run there. The root `.gemini/.env` is protected (above). A plain `.env` stays writable, because applications use it. Instead sandy records every `.env` and `.gemini/.env` in the workspace root and up to 4 directory levels below it at launch, and at session end lists any that were created or changed, with no removal command (the file may be yours). It also reports a link named `.gemini`, a FIFO or a directory named `.env`, and any directory it can enter but not list. It does not look inside `.git`, `node_modules`, `.venv`, `venv`, `vendor`, `__pycache__`, `.tox`, `.mypy_cache`, `.pytest_cache`, `.cache` or `target`, or through a linked directory. This is detection only: review a reported file before you run `gemini` on the host in that directory.

**Sandbox-mounted directories** — when the workspace has one of these directories, the session sees a writable sandbox copy mounted over it instead of the host directory:

| Path | Behavior |
|---|---|
| `.claude/commands/` | Claude's slash commands. The copy can gain new ones without touching the host |
| `.claude/agents/` | Claude's agents. The copy can gain new ones without touching the host |
| `.claude/plugins/` | Managed via `/plugin install` inside the container |

`.gemini/extensions/` and `.gemini/commands/` work the same way for Gemini. The sandbox's copy is made the first time a launch finds the directory in the workspace. If it has content then, the copy starts with that content; if it is empty then, the copy starts empty. After that the copy is kept: later host edits do not reach the sandbox, and the agent's edits stay in the sandbox. `sandy --reset-sandbox` discards the copies, along with the rest of the sandbox's agent state, so the next launch makes them afresh. **If the workspace has no such directory (and the sandbox has no copy yet), sandy mounts nothing there**, so anything the agent creates at that path lands in the workspace on the host. If that path is a symlink (or sits under one, such as `.claude -> elsewhere`) pointing outside the workspace, the dangerous-symlink prompt asks about it, wherever it points. Approved, the sandbox gets a copy of the target's contents, and the agent's changes stay in the sandbox. The copy that is mounted is always a real directory, never a link. Since 2.9.0, sandy refuses to launch a sandbox whose copy is still a link left by an earlier version, and tells you the `rm` command that fixes it. Sandy's cleanup of empty leftover directories (`.github/workflows/` and the overlay stubs) never removes anything through a symlink.

**Mount policy (existence-gated).** Protected files and directories are mounted read-only only when they exist on the host — a path the host doesn't have gets no mount (an always-mount-with-empty-stubs approach was tried and reverted: the stubs polluted `git status`, broke `direnv`, and confused IDE scanners). The trade-off is covered by **session-end detection**: sandy records which protected paths existed at launch, and on exit warns about any protected file or directory that newly appeared (e.g. an agent-written `.git/hooks/post-checkout` or `.github/workflows/ci.yml`), with the remediation command — so you can review it before the next `git pull`/`push`/IDE-open would fire it. The same warning covers `.claude/commands/`, `.claude/agents/`, `.claude/plugins/`, `.gemini/extensions/` and `.gemini/commands/`: their sandbox copy is mounted only when the directory exists at launch and the agent that reads it (Claude for `.claude/`, Gemini for `.gemini/`) is in the session, so one an agent creates in a workspace that had none, or writes into while no copy covers it, lands on the host, where your own Claude Code or Gemini CLI reads it. It also covers `.claude/skills/`, which gets no sandbox copy at all, so the agent can write skills there and they reach the host: sandy reports one created during the session, and any change to one that existed at launch, so you can review it before your own Claude Code loads it. Since 2.10.1 the same goes for `.gemini/agents/`, `.gemini/skills/`, `.gemini/policies/` and `.agents/skills/`, which also get no sandbox copy: a Gemini CLI on your host loads subagent definitions from `.gemini/agents/*.md` (a subagent can declare MCP servers, which are commands Gemini CLI runs on your host once you acknowledge the subagent), workspace skills from `.gemini/skills/` and `.agents/skills/` (other agent CLIs read `.agents/skills/` too), and, if Google re-enables them, workspace policies from `.gemini/policies/`. To tell a change, sandy lists and hashes each of these whole trees at launch and at exit (and `.gemini/extensions/` when no Gemini copy covers it), which takes longer the more it holds, for example a skill that bundles its own `node_modules/`. If a reported path is a symbolic link, the warning shows where it points and suggests a plain `rm` of the link, never `rm -rf` through it. A [daemon session](daemon.md#the-session-end-report-of-a-daemon-session) has no terminal to print to, so it also records the warning in its sandbox, and the next `--start`, `--attach`, `--stop` or terminal launch of the workspace shows it until `sandy --ack-report`.

**Caveat — a host IDE on the shared workspace.** Sandy's protection assumes the *host* isn't independently reading the workspace while the agent runs. A common setup breaks that assumption: the same project directory open in a host IDE (VS Code, Cursor, JetBrains) at the same time as the sandy session. The workspace is bind-mounted read/write, so an auto-execution config the agent writes into it — `.vscode/tasks.json`, a `.githooks/` script, a `.devcontainer/`, a `.claude/settings.json` hook — can be run by that host IDE, entirely outside sandy's boundary. Sandy blocks the common vectors *when they exist at launch* (the read-only mounts above) and warns at session end about newly-appeared ones, but this is existence-gated **detection, not prevention**: an absent `.vscode/` is unprotected in-session, and the end-of-session warning can be missed before the IDE auto-runs the file. When working an untrusted repository, don't leave the same workspace open in a host IDE during the session — read sandy's session-end report first.
